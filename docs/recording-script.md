# Screen recording script (target 8–9 minutes, hard limit 10)

**Goal of the video:** show one live run end to end, from extraction to the AI-generated post to the published post on the test Facebook Page, and explain the decisions that make it production-minded. Speak to the *why*; the canvas notes carry the *what*.

## Before you hit record (checklist)

- [ ] `.env`: `PW_DRY_RUN=false`, `PW_REVIEW_MODE=auto` (switch to `approval` for segment 6), `PW_FB_PAGE_ID` = your **test** Page, `PW_TELEGRAM_CHAT_ID` set. `docker compose up -d` after edits.
- [ ] Credentials green in n8n; run the workflow once off-camera to confirm (then delete that test post from the Page or leave it, it will not be picked again).
- [ ] Tabs open, in this order: ① n8n editor with the daily workflow (zoomed to fit), ② the test Facebook Page, ③ Telegram (desktop or phone mirrored), ④ the dashboard `…/webhook/placidway-dashboard`, ⑤ README on GitHub.
- [ ] Optional terminal/psql tab: `SELECT status, content_key, fb_post_id, error_code FROM pw_run_log ORDER BY id DESC LIMIT 5;`
- [ ] Hide bookmarks/notifications; browser zoom 110–125 % so node names are readable; microphone check.
- [ ] Keep the item-picking deterministic: the weekday rotation decides the content type (Mon article, Tue package, Wed Q&A…). Know which type today's run will choose.

## Script

| Time | Screen | What to say (narration) |
|---|---|---|
| **0:00 – 0:30** | README top (requirements table) | "Hi, I'm Iman. This is a daily PlacidWay-to-Facebook automation built on self-hosted n8n with Postgres. Every day it picks one fresh article, package or patient Q&A from PlacidWay's public pages, writes an on-brand post with an LLM, verifies every claim against the page, and publishes it to my test Page, with an optional human approval step. I'll do a live run, then walk through the decisions." |
| **0:30 – 1:30** | n8n canvas, zoomed to fit. Hover each coloured stage. | "The canvas reads left to right in seven stages. **1** triggers: a daily schedule at 9, with retry slots at 11 and 2 that exit immediately if today's post exists, plus a manual trigger. **2** polite extraction. **3** selection and de-duplication. **4** generation and two-layer guardrails. **5** the optional approval lane. **6** publishing. **7** a single exit: every run, success or failure, goes through the same logging and alerting tail. The logic in the Code nodes is plain JavaScript that's unit-tested in the repo and built into this file." |
| **1:30 – 2:00** | Click **Execute workflow**. While it runs, open the **Config** node output. | "Configuration is environment-driven: dry run, review mode, publish now or schedule, timezone, page ID. No secrets here; keys live in n8n's encrypted credentials. I'm running live, auto mode." |
| **2:00 – 3:15** | Click through: **Fetch robots.txt** → **Plan listing requests** → **Fetch listing pages** → **Select candidates** (show `selection_reason`) → **Extract & validate content** (show title, summary, image_url, body excerpt). | "First robots.txt, enforced with an RFC 9309 parser: if it's unreachable we stop. Then the three listing pages (articles, packages, Q&A) sorted by modified date. They act as feeds: one request per type, about six requests a day, at least 1.5 seconds apart. Why not RSS or sitemaps? There's no RSS for this content, and the sitemaps are HTML lists of a thousand titles without dates. No headless browser either: pages are server-rendered. Selection excludes everything already used in Postgres, prefers today's content type, and avoids repeating a treatment category. Extraction uses the Open Graph tags for title, summary and image, and main-content text for facts. It stops before 'related packages' sections, so another clinic's price can never become a fact for this post." |
| **3:15 – 4:30** | **DB: claim item** → **LLM: generate variants** (show 3 variants) → **Guardrails: rule checks** (open a variant's `rules`) → **LLM: compliance judge** → **Guardrails: final decision** (show `report.variants`, chosen index, `post.text`, `chars_before_link`). | "The item is claimed atomically in Postgres before any tokens are spent, so even two overlapping runs can't post the same URL. The model returns three variants as structured JSON (hook, lines, CTA, hashtags, plus verbatim evidence) and code assembles the post, so the link position and the 500-character limit are exact. Layer one is deterministic: banned medical-claim and outcome words, every number or price must exist in the source, no credentials the page doesn't state, and the cited evidence must really be in the page. Layer two is an LLM judge that checks each claim against the source. We publish only what passes both; if nothing passes, the item is blocked and I get an alert with the reasons. It fails closed." |
| **4:30 – 5:30** | **Build publish plan** → **Facebook: publish post** (status 200, `post_id`) → **Facebook: get permalink** → **Outcome: success** → **DB: finalize run** → **Telegram: notify**. Switch to the **Facebook Page tab**, refresh, show the post with image and link. Click the link → PlacidWay page. | "It posts a photo with the featured image, using PlacidWay's 1200 by 630 rendition. If Facebook rejects the image, it automatically falls back to a link post. Here's the post on my test Page: hook, value lines, CTA, link, hashtags, disclaimer, and the image. And here's the Telegram notification with the permalink." |
| **5:30 – 6:15** | **Dashboard tab** (refresh), then optionally the psql query. | "Every run is logged: item, post text, Facebook post ID, status, duration, the full guardrail report and token usage. This dashboard is a small n8n webhook workflow over the same tables; a second workflow reads back reactions, comments, shares and clicks every six hours." |
| **6:15 – 7:30** | Set `PW_REVIEW_MODE=approval` beforehand in a duplicated run, or show a pre-recorded approval: Telegram draft message → tap **Approve** → n8n execution resumes → post appears. | "For a medical brand I'd start in approval mode. The draft, source link, image and guardrail evidence go to Telegram with signed approve and reject links; the execution simply pauses. Bots are ignored, so Telegram's link-preview crawler can't approve anything; I tested that. Approve, and it publishes; reject or ignore it, and nothing goes out." |
| **7:30 – 8:30** | Executions list: open a failed execution (e.g. run with `PW_BASE_URL` pointing to a dead host, or show the `SITE_DOWN` alert in Telegram). Show the alert text with the error code and "Next step". | "Failures are never silent. Requests that are safe to repeat are retried with backoff; the Facebook post itself is not, because a retry after a timed-out success would double-post. The afternoon slots retry the whole run, and failed items get up to three attempts. Every failure is classified (site down, token expired, LLM auth, rate limit) and the alert says what to do. The run is still marked failed in n8n, and anything unexpected is caught by the error trigger, without duplicate alerts." |
| **8:30 – 9:00** | README "Limits, trade-offs" section | "Main trade-offs: the parser depends on PlacidWay's URL patterns, so it fails loudly with PARSER_BROKEN instead of guessing; the judge is probabilistic, which is why the rules and approval mode exist. The repo has 37 unit and SQL tests and 15 end-to-end scenarios run against the exported workflow in a real n8n instance. Thanks!" |

## If something goes wrong on camera
- The run is idempotent: just click **Execute workflow** again; it picks the next item.
- If the LLM blocks today's item (guardrails), say so: it's a feature. Show the alert, then run again.
- If Facebook is slow, show the `Simulate publish`/dry-run output and the previous published post on the Page.

## Recording tips
- Use OBS or Loom at 1080p, 30 fps; record the browser window only.
- Pin n8n's output panel to *JSON* or *Table* view and collapse long fields before recording.
- Keep a sticky note with the timestamps above open on a second screen.
